01 / Executive Summary

What DA and DVA do, and what this document asks Honeywell to approve

Deployment Agent (DA) is the reasoning orchestrator: it reads a Jira ticket, classifies it, and drives it to exactly one pull request per ticket — then stops. Deployment Validation Agent (DVA) is a deterministic validation service with no model access: fixed contracts, hardcoded query tools, Reader-only rights, pass/fail out. Together they hold to one governing line: DA reasons and proposes; DVA observes and reports; humans and DevOps-owned pipelines dispose. No component holds two of those three roles, which is what makes each one auditable on its own.

This document is the single buildable design for both agents, reconciling the BRD, five prior workflow drafts, and three DVA documents into one reference. It closes every requirement in the BRD (R-001 through R-012, Section 09), answers every item raised across two review cycles (Section 15), and states plainly where a capability is structurally absent rather than policy-restricted (Section 10).

Status, stated plainly. Nine decisions need a call from Honeywell before build — each named by owner and given a recommended default in Section 15. Zero items block approving the design itself. The architecture, the DA↔DVA contract, the HITL register, and the governance model are final and buildable as written; the nine open decisions can be resolved in parallel with build kickoff, not in front of it. Section 16 lays out that path.
02 / Finalized Design Decisions

What was decided, and what it replaces

The source material carried three competing designs. This section fixes one, so the build has a single reference. Everything downstream in this document follows from these eight decisions.

#DecisionWhat it replaces, and why
D1 — DVA has no LLMDVA is a stateless FastAPI service built entirely from deterministic, hardcoded tool calls: fixed Pydantic request/response models, per-resource-type KQL templates held in a static registry, and direct ARM GETs. No model, no prompt, no synthesized query, no natural-language parsing anywhere in the process.The DVA documents described it as an “AI-assisted microservice” with the LLM acting as a “parameter-extraction and decision engine.” That role is removed. Every input DVA needs is already structured by the caller, so a model adds latency and non-determinism to a step whose entire value is being trustworthy. A validation gate that can hallucinate is not a gate.
D2 — DA is the only LLM holderModel reasoning is confined to DA, and inside DA to four bounded jobs: parse the ticket (Step 1), classify it (Step 2), split it into work items (Step 2b), and phrase HITL questions. Every consequential action — registry lookup, folder scan, variable matching, closure proof, render, validate, commit — is deterministic code.Earlier drafts had the LLM doing risk scoring and validation judgement (validate_request with “Full Picture LLM Validation”). Removed: a model must never be the thing that decides a deployment is safe.
D3 — DA.md is the structural authorityStep / Gate / HITL numbering from DA.md is canonical, including the per-item fan-out, the fan-in batching at HITL 5, the 4a.5 closure proof, and the per-ticket retry cap of three.Supersedes the LangGraph node naming (Node 1…6) of workflow 2/3/4. Those node names survive only as an implementation detail, mapped in Section 05.
D4 — DVA is called from two placesMode 1 (PreCheck / Discovery, Azure Resource Graph) is called by DA at Step 4b. Mode 2 (PostProvision / Gate, direct ARM) is called by the CI/CD pipeline before every promotion, with no DA involvement. Both are built once, in one service, behind two endpoints.Closes the largest gap in the prior draft: R-011 requires an independent pipeline gate, and no diagram showed it. D5 — DA has no post-merge roleDA’s authority ends at Step 6, when the PR is open. D6 — Pipeline link is an explicit stepNew Step 5.1 — Notify: post the PR URL to the ticket on PR creation, and the GitHub Actions run URL for the roughly 45-minute provisioning job once it exists.R-005 requires this and DA.md had no step for it. D7 — Tagging is enforced at renderStep 4c injects a mandatory tag block — Project, Environment, ManagedBy=deployment-agent, TicketID, Requester — and Step 4a.5 fails closed if it is absent or empty.R-010 and objective O5 need a mechanical guarantee, not a convention. D8 — The contract is versioned firstThe DA↔DVA schema is defined in Section 07, served under /v1/, and changed additively only. Fixed machine-readable reason codes; no free-text-only failures.Neither source document specified field names or error shape. With two independent callers, an unversioned contract means a change on one side silently breaks the other.
D9 — DA never calls a model provider directlyDA's four LLM calls (Step 1, Step 2, Step 2b, HITL phrasing) are served through either Azure AI Foundry or Databricks Model Serving External Models — never a direct SDK call to Anthropic, OpenAI, or any provider. This design fixes that: a direct provider call would put credential rotation, rate limits, and model governance inside DA's own code instead of the platform layer every other agent in this ecosystem already shares.
The single sentence that governs the whole design: DA reasons and proposes; DVA observes and reports; humans and DevOps-owned pipelines dispose. No component holds two of those three roles, which is what makes each one auditable on its own.

04 / DA Shared Entry

Intake, Gate A, Classify

Common to all three classifications. This is the only place DA converts free text into structure, and the only place it decides which branch a ticket belongs to.

Gate A rejects before it clarifies. The first question Gate A answers is not “are the fields present” but “is this DA’s job at all” — a ticket asking for a firewall rule change or a database restore exits here rather than being coerced into one of the three branches. Only after intent is confirmed does the missing-field loop run.

06 / DVA — Deterministic Build

One service, two endpoints, no model

DVA answers one question — does this Azure resource exist, and is it healthy? Two engines answer it, chosen by which kind of wrong answer would hurt more: cross-subscription reach, or freshness.

What DVA is

  • A stateless FastAPI service, horizontally scalable behind a load balancer because it holds no session and no state.
  • Fixed Pydantic request and response models. Malformed input is rejected before any Azure call is made.
  • A static registry of per-resource-type query tools: KQL templates for Mode 1, ARM paths for Mode 2. Templates are parameterised, never string-built from user text.
  • Generic-first: one code path covers the large majority of resource types — ID structure, API-version resolution, HTTP GET, Succeeded state. Specialized checks (Key Vault firewall, SQL DB firewall) are pluggable decorators that extend the generic result rather than replacing it.
  • Reader role only, via system-assigned Managed Identity in Azure container runtimes; Service Principal for local development.

What DVA structurally is not

  • Not model-backed. No LLM client, no prompt, no API key, no fallback to a model on an unrecognised input. An unknown resource type returns a typed UNSUPPORTED_TYPE error, not a guess.
  • Not a query generator. KQL and ARM URLs are never synthesized from natural language — the callers supply structured coordinates.
  • Not a writer. No provisioning, no remediation, no tagging, no state store. */Write and Microsoft.Authorization/*/Write are outside its role assignment, so a bug cannot become a change.
  • Not DA-coupled. It does not know what Jira is. Requests from DA, a GitHub Action, an Azure DevOps pipeline, or curl are indistinguishable to it.
  • Not authoritative on intent. It reports reality; the caller owns what “should” exist.

Why the gate matters in practice

Mode 2 exists because of what happens without it. A promotion pipeline with no infrastructure check deploys code into an environment that is silently missing a dependency — a Redis instance, a database, a storage account — and the gap only surfaces at runtime, as a crashing pod or a connection failure, with nothing telling the on-call engineer what actually went wrong. With the gate in place, that same gap is caught before code ever reaches the environment: the pipeline halts with a named resource and a typed reason code, not a stack trace to reverse-engineer.

What the gate buys, concretely. It moves the failure earlier — a missing dependency is caught before code deploys, not after a pod crashes. It replaces open-ended debugging with a named resource and a reason code, so the fix is provision-and-retrigger rather than investigate-from-scratch. It runs the identical deterministic check on every promotion, so the outcome does not depend on which engineer is on call that day. And because it is a hard blocker rather than an advisory step, there is no path by which a missing dependency reaches production silently.

07 / DA ↔ DVA Contract & KPIs

Endpoints, reason codes, and performance targets

DA and DVA talk through two versioned REST endpoints. The contract is defined here so neither side has to infer a shape — callers send structured coordinates in, and typed pass/fail verdicts come out. Performance targets are drawn from the baseline harness runs across all three request categories.

Mode 1 — PreCheck / Discovery  POST /v1/precheck

DA sends every surviving work item in a single call once Step 4a has resolved each resource_prefix. The request carries a correlation ID, the ticket and environment, the target subscription, and per-item coordinates — category, resource type, name, and resource group. The response returns an azure_side flag per item (present, absent, or indeterminate) plus a summary count. DA folds each azure_side flag with the code-side flag from Step 3b to resolve the quadrant. A throttled or errored ARG call returns indeterminate rather than absent — collapsing the two would allow DA to propose creating a resource that already exists, which is the duplicate-creation risk ARG pre-check exists to prevent. On indeterminate, DA exits to HITL rather than guessing.

Mode 2 — PostProvision / Gate  POST /v1/validate

Any CI/CD runner sends fully qualified resource IDs, or explicit coordinates from which DVA constructs an ID deterministically. DVA resolves the API version, queries the ARM endpoint directly, and inspects provisioningState. The response carries a verdict (PASS or FAIL), an exit code the pipeline step acts on directly, a count of checked, passed, and failed resources, and per-failure detail including a typed reason code, the observed state, and a remediation link. A resource in any state other than Succeeded fails the gate — Unknown is not a pass, and an access error is reported as ACCESS_DENIED rather than silently treated as absence.

Versioning

Both endpoints are served under /v1/. Fields may be added additively; existing field names, types, and reason-code meanings may not change within a version. Callers must treat an unrecognised reason code as a failure, never as a pass — this means a DVA-side addition can never silently open a gate.

Reason codes
CodeMeaning, and what the caller should do

10 / Governance & Security

Capabilities that do not exist

The two lists below are the security model. They are not configuration — they describe capabilities absent from each component’s credentials and code paths, which is why they cannot be turned on by a prompt, a bug, or a bad ticket.

What DA structurally cannot do

  • Approve its own PR.
  • Merge a PR.
  • Run terraform or terragrunt apply.
  • Modify the central modules repository.
  • Rename an existing folder — names are immutable once applied, being embedded in the tfstate path.
  • Fall back to ?ref=main — a real resolved tag is required at Step 3.
  • Write a secret value directly — sealing is delegated to scripts/appsettings.py.
  • Hardcode an environment value — environment data resolves through pointers, never literals.
  • Target production directly.
  • Edit an existing terragrunt.hcl — additions only, in this version.
  • Act after merge — post-merge verification belongs to DVA Mode 2 (D5).

What DVA structurally cannot do

  • Call a model — no LLM client, key, or prompt exists in the service (D1).
  • Write anything — */Write and Microsoft.Authorization/*/Write are outside its role assignment.
  • Provision or remediate what it validates. It reports; someone else fixes.
  • Persist state — no database, no session, no queue.
  • Synthesize a query — KQL and ARM paths come from a static registry with bound parameters.
  • Interpret intent — it consumes structured coordinates and is indifferent to their origin.
  • Guess on an unknown type — returns UNSUPPORTED_TYPE rather than a default pass.
  • Treat an access error as absence — ACCESS_DENIED is its own reason code.
  • Pass on an unreadable state — Unknown fails by design.
Where the human checkpoints sit
CheckpointOwnerWhat is decided
HITL loops and exitsRequester / DevOpsWhether the request is complete, correctly split, and unambiguous. Section 08 lists all of them.
PR validationPipelinefmt, validate, plan, OPA. Must show N to add and 0 to destroy. Azure is unchanged. A destroy or OPA violation rejects the PR.
CODEOWNERS approvalHumanThe irreversible decision. The agent has no vote and no bypass.
Environment approval gateHumanInside provision_infra.yaml, after merge and before apply — a second deliberate pause on the only step that changes Azure.

DVA security posture
  • Authentication by system-assigned Managed Identity inside Azure container runtimes; Service Principal credentials for local development only.
  • Least-privilege RBAC: standard Reader across the subscriptions in scope, and nothing more. A DVA compromise yields read access, not write access.
  • Every validation run carries a correlation ID, traced across the coordinate validator, identity resolver, version resolver, and query client, giving an auditable path for security review.
  • Inputs are rejected by schema before any Azure call, which keeps malformed or hostile input away from the query layer entirely.

12 / Scope — In & Out

What DA and DVA each do, and what neither of them does

Everything below already exists in this document as a decision, a requirement, or a structural guarantee — this section is that same material, pulled into one place so scope is a single answer, not something assembled by reading every prior section.

Deployment Agent (DA)

IN SCOPE

  • Read a Jira ticket and classify it into Cloud Service/IaC, Microservice Onboarding, or Config Change (R-001, R-002)
  • Check whether a named Azure resource already exists, via DVA Mode 1 (R-003)
  • Discover the matching IaC module and resolve a real git tag, never main (R-004)
  • Split a ticket into N work items and get the user to confirm the split
  • Resolve every module variable through six deterministic checks, and prove closure before rendering
  • Render Terraform/Terragrunt (Section A), Kubernetes manifests from golden templates (Section B), or a surgical YAML mutation (Section C)
  • Inject the mandatory tag block on every resource (R-010)
  • Open exactly one PR per ticket, and post the PR + provisioning-run link back to the ticket (R-005, R-007)

OUT OF SCOPE — structurally, not by policy

  • Approving or merging its own PR, or running terraform apply / terragrunt apply (R-009, D5)
  • Modifying the central IaC module registry, or renaming a folder once applied
  • Writing a raw secret value directly — sealing is delegated to scripts/appsettings.py
  • Targeting production directly, or editing an existing terragrunt.hcl (additions only, this version)
  • Any action after merge — post-merge verification belongs entirely to DVA Mode 2 (D5)
  • Databricks and Unity Catalog requests — explicitly named as lacking IaC modules; these land in the gap register by design, not by omission
  • Story-point-free — not applicable to this agent; there is no equivalent artifact-estimation concern in DA's own scope
Deployment Validation Agent (DVA)

IN SCOPE

  • Mode 1 — PreCheck/Discovery via Azure Resource Graph, called by DA at Step 4b
  • Mode 2 — PostProvision/Gate via direct ARM GET, called by any CI/CD runner before every promotion, independent of DA (R-011, R-012)
  • Typed pass/fail verdicts with fixed reason codes and remediation links, versioned under /v1/
  • Specialized policy checks (Key Vault firewall, SQL firewall) as pluggable decorators on the generic result

OUT OF SCOPE — structurally, not by policy

  • Any model access whatsoever — no LLM client, key, or prompt exists in the service (D1)
  • Any write path — */Write and Microsoft.Authorization/*/Write are outside its role assignment
  • Provisioning or remediating what it validates — it reports, and someone else fixes
  • Persisting state, session, or a queue — the 24h API-version cache is the only in-memory state, and it is disposable
  • AKS workload/pod health polling — explicitly out of v1 (removed in D5; see Section 15 for the full answer on Kubernetes-layer validation)
13 / Automation vs. LLM — Where Each Runs, and What the LLM Is Worth

Four LLM calls in the entire system. Everything else is code.

Section 05 already draws the line between model reasoning and deterministic code (D1, D2). This section goes one step further, per RAIL-01's own charge to "clearly differentiate AI/LLM activities from deterministic automation activities": not just where the model runs, but what it is actually worth at each point, and whether all four calls earn their place. The table below is every named step in DA and DVA, tagged plainly — nothing summarized away.

The complete plane — every step, tagged

Three independent tags per step, not one: AUTOMATION deterministic code that runs regardless; LLM the model generates something; LLM VERIFY a proposed, advisory-only model review layered on top of an automation step, sanity-checking its output without ever being the thing that blocks or passes it (D2 still holds — see the callout below); HITL a human checkpoint from the Section 08 register actually sits at this step. The LLM-verify column is a recommendation, not a decision already taken. Nothing in the Consolidated Solution today runs a model over any deterministic step's output — D1 and D2 stand unchanged, and DVA is excluded from this idea entirely, with no exception. Where LLM VERIFY appears above, it is advisory by design: a flag surfaced alongside the existing HITL checkpoint or PR body, never a pass/fail signal of its own, and never in the path of the deterministic gate it sits next to. The seven steps it is proposed for share one property: their deterministic check is structural (does this parse, does this key exist) rather than semantic (does this value actually make sense) — exactly the gap Section 05's own test names ("would a human reviewer notice if this were wrong by reading the PR?"). The other twenty automation steps don't need it, because their failure mode is already loud, binary, and already caught. Honeywell's platform/product owner decides whether to build it — the same way D1–D9 were each a deliberate decision rather than a default. Recommended default if this needs to move forward without further discussion: build it, scoped to exactly these seven steps and gated to stay advisory-only, consistent with D1 and D2.
The four LLM steps, individually — justified or not
StepWhat the LLM does hereWhy it's justified — or isn't
Step 1 — IntakeParses free-text Jira ticket content into structured JSON (service, env, resources, inputs)Justified. This is the one place genuinely unstructured human language enters the system. Every deterministic check downstream depends on this structure existing — rule-based parsing would need the ticket format itself to be constrained, which the BRD does not assume
Step 2 — ClassifyRoutes the parsed ticket into Cloud Service/IaC, Microservice, or Config ChangeJustified, with a caveat. A clear ticket ("add a Redis cache") barely needs a model — the value is concentrated in the ambiguous middle, a ticket that could be read as either a new microservice or a config change on an existing one. How often that ambiguous middle occurs in Honeywell's real tickets is a question a golden-set evaluation against real ticket history answers directly; running that evaluation is a recommended pre-build validation step, not a prerequisite for approving this design
Step 2b — SplitDecomposes one ticket into N work items, then asks the user to confirm the split before anything else runsJustified, by design. This is the one LLM step the design deliberately does not let stand alone — a mandatory confirmation step follows it immediately, with HITL 3 if the user says the split is wrong. That pairing is the pattern to use anywhere a probabilistic step needs a cheap, immediate human check rather than downstream cleanup
HITL phrasingTurns the collected variable gaps (already fully structured — resource name, variable name, example value) into one readable messageNot justified as an LLM call. By the time this runs, every fact it needs is already a typed value from Step 4a.3's own six checks. "Managed-Redis needs sku_name (e.g. Balanced_B3)" is a string template away from the data that already exists — this is a real candidate to become a plain formatting function, not a model call. Doing so removes one source of latency and non-determinism for zero loss of capability.
The same split, as properties rather than steps

Independent of which specific step is being discussed, this is why the split above lands where it does.

PropertyLLMAutomation
ReproducibilityLow — the same input can produce a different outputDeterministic — the same input produces the same output, every time
AuditabilityMedium — the output is readable, but not fully explainableEvery step is traceable and explainable
Handling ambiguityStrong — navigates fuzzy, unstructured inputWeak — needs structured input, fails on edge cases
Latency predictabilityMedium — token count varies, completion time is not fixedStrong — bounded operations, predictable timing
Failure recoveryMedium — can escalate to HITL, but needs a human in the loop to proceedStrong — failures are clean; exit codes drive the next automated step
Cost per callHigher — model tokens plus inference latencyLower — simple operations, cacheable where the input repeats
The total, stated plainly. Across the entire DA flow — shared entry, all three branches, DVA's two modes — 27 named steps exist. Four touch an LLM. The other twenty-three are registry lookups, git-tag resolution, six-way variable matching, closure proofs, template rendering, kustomize validation, and API calls — all of them deterministic, all of them reproducible: the same input produces the same output every time, which is exactly the property Section 05's own test ("would a human reviewer notice if this were wrong by reading the PR?") requires of everything that isn't the model. DVA holds zero of the four — its whole reason to exist (D1) is that a validation gate with any model exposure is not a gate.
What this means for how much value the LLM is providing. By volume, not much: three narrow, bounded jobs, each scoped to the exact place free text meets a fully deterministic pipeline, plus HITL phrasing — identified as a v1.1 simplification opportunity, deterministic templating rather than a model call, not a v1 blocker. That is not a weakness of this design — it is the design working as intended. The BRD's own pain point is "engineers manually decomposing thin Jira descriptions"; DA's LLM footprint is sized to solve exactly that problem and stop, rather than reaching for model judgement anywhere confidence, auditability, or reproducibility would suffer for it (D2). A system that used the model for more than this would be working against the design principle in Section 02, not with it.
14 / LLM Sourcing (D9)

Where the four LLM calls actually come from

Section 13 fixed what needs a model. This fixes where that model is served from — a decision this design makes explicitly, replacing the direct Anthropic SDK call the prior drafts had defaulted to without deciding (Toolchain & Runtimes, Access & Environment Requirements doc). Full build and connectivity detail — endpoint formats, auth flows, SDK calls, environment variables — lives in the dedicated companion document, DA_LLM_Sourcing_and_Connectivity_Solution.html. This section is the decision and the comparison; that one is how to build it.

Why this needed its own decision. DA is Azure-native everywhere else — Managed Identity for Key Vault, direct ARM/ARG-adjacent calls via DVA, GitHub App tokens, a Jira service account. Reaching for a third-party provider SDK for exactly four narrow calls means a new credential type, a new rotation schedule, and a new place secrets and rate limits live, none of which anything else in DA's design needs. That mismatch is what D9 closes.

Recommendation, not a mandate. Azure AI Foundry is the better default for DA specifically, because DA's own design never needed a second identity system anywhere else — adding one purely to reach an LLM is the mismatch D9 exists to close. The case for Databricks Model Serving instead is real but conditional: it wins if Honeywell wants one shared place to see and govern every agent's LLM calls across the whole ecosystem (DA included) — a platform-level decision bigger than DA on its own, and Honeywell's to make. Absent that platform-wide preference, build DA against Azure AI Foundry.

Kubernetes (AKS) validation, stated directly

In v1, DVA does not validate AKS workload or pod health for Sections B and C. Its Mode 2 gate checks the ARM-level resource state only — existence and provisioningState — the same check it runs for any Azure resource, not whether a pod is actually running and ready inside the cluster. Extending that to real workload health is a named, scoped v2 addition: DVA would need Reader on the AKS resource and, for pod-level state, a ClusterRole inside the cluster itself — a materially different, cluster-internal credential that this design does not request for v1. Honeywell's platform team owns whether workload-health validation moves into v1 scope; the recommended default is to build v1 as specified and add it as a scoped v2 increment.

Promotion, made the visible primary path
What the 17 September review asked for. The reviewing architects' own words: promotion workflows "happen repeatedly and provide immediate value," while Section A's cloud-service/IaC creation flow is comparatively rare. The review's recorded outcome: agreed to make promotion use cases more visible in how this design is presented; fresh environment creation stays in scope, unchanged. Six steps carry every promotion the same way they carry every creation request:

1 — Intake

Jira ticket read (Step 1), same for a creation request or a promotion event.

2 — Classification

Route into Section A/B/C (Step 2) — for promotion specifically, this is what determines whether the target is Terraform-managed infrastructure or a GitOps-managed microservice/config.

3 — Gap collection

The six-way variable match and closure proof (Step 4a/4a.5) — for a promotion, this resolves which values (SKU, region, replica counts) differ per target environment, not just whether a resource is new.

4 — PR creation

Step 5 — one PR into the target environment branch, whether the change is a new resource or a promoted change to an existing one.

5 — Validation

validation.yaml (plan, OPA) plus DVA Mode 1's embedded existence check (Step 4b) — Azure is unchanged at this point either way.

6 — Promotion

DVA Mode 2 — the independent gate before every environment promotion (R-011), regardless of which pipeline or PR produced the change being promoted.

This is the executive-level version of Section 03's full architecture diagram — six nodes, no quadrant logic, no Section A/B/C branching detail. Use this one for sponsor-level review; keep Section 03 as the engineering reference.

DEVFirst promotion target. DVA Mode 2 gate runs before this promotion exactly as it does for every later one — dev is not a lower-rigor environment in this design.
